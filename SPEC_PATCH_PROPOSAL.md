## 0. Canonical definitions (referenced by the patches)

**Coverage snapshot (C1).** One concept: `universe_coverage_snapshot`, with `scope ∈ {ACQUISITION_BATCH, DISCOVERY_RUN, SETUP_SCAN}`. Holds intended / in-scope / observed counts, out-of-scope exclusions with reasons, per-state evaluation counts (C3) and per-field counts by value state (N10), plus `universe_status ∈ {OBSERVED_ONLY, VERIFIED_AGAINST_MASTER}` and `data_vintage_id`. Replaces `discovery_universe_snapshot`, `discovery_coverage_snapshot`, `setup_scan_coverage` (kept as historical aliases in Doc 14 §A–§I).

**Evaluation identity (C2, revised).** Four concepts, none standing in for another:
1. **Setup occurrence key** (conceptual) = `setup_definition_version_id + security_id + evaluation_as_of`. It names "this rule version, this security, this market time". It has no scan and no data version in it. A `setup_instance` exists for an occurrence key when at least one evaluation record for it is `EVALUATED_MATCHED`.
2. **Scan membership** = `scan_run_id + security_id + evaluation_as_of`. It is only the denominator declaration: this security-time was `IN_SCOPE` of the scan's intended universe, or `EXCLUDED_FROM_SCOPE` (+ reason). It carries no setup version and no match result, so several setup definitions in one scan cannot collide.
3. **Evaluation record** = one row per setup definition evaluated for a security-time in a scan. Unique `evaluation_id`; natural key `scan_run_id + setup_definition_version_id + security_id + evaluation_as_of + data_vintage_id`. Holds exactly one evaluation state, reason code, feature-snapshot reference, `evaluated_at`. Immutable.
4. **Data vintage** (see N9 below), explicit in the key and on the record even though a scan run uses exactly one vintage. This keeps provenance explicit after export, copy or any later change to scan design.

**Repeated evaluation of the same conceptual occurrence.**
- Same occurrence key, **different vintage** → a different evaluation record (new `evaluation_id`) with its own state, feature snapshot and outcome. Earlier records are never updated. The same occurrence may be MATCHED on vintage V1 and NOT_MATCHED on V2; both stay visible.
- Same occurrence key, same vintage, **different scan run** (rerun, other experiment) → a different evaluation record. With a deterministic setup version the state must be identical; a difference is a defect flag, not a new truth.
- An "occurrence history" view lists evaluation records ordered by vintage. No record is silently "current". A study declares which vintage it uses; a later vintage is not automatically more correct.

**Evaluation state (C3, revised).** Exactly one per **evaluation record**, precedence:
1. `EXCLUDED_INELIGIBLE` (setup-version rule excludes this security-time; reason code)
2. `UNEVALUABLE_REQUIRED_DATA_MISSING` (reason: which required trigger input is missing, in what value state, or insufficient history)
3. `EVALUATED_NOT_MATCHED`
4. `EVALUATED_MATCHED`
Counts per scan and setup version: in-scope = number of `IN_SCOPE` memberships; in-scope = sum of the four states; eligible = in-scope − (1); evaluable = eligible − (2); matched = (4). Out-of-scope memberships are reported separately. "Scanned" and "evaluated" are not separate counts. All records (all four states) are retained; large matrices in versioned Parquet per Doc 18 §4.

**Data vintage (N9).**
- *Definition:* the exact set of input artifact versions (source route, trading date, artifact hash, `retrieved_at`) selected under a stated selection rule and cutoff (e.g. "latest artifact per date retrieved on or before cutoff T"), plus normalization-map version, price-basis and corporate-action basis, trading-calendar version and metric/feature definition versions. Its identifier is derived from that content, so identical inputs give the same vintage id and any difference gives a new one.
- *Immutability:* once referenced by any evaluation it never changes. A corrected or revised artifact, a new normalization map or a new corporate-action basis creates a **new** vintage; it never edits an old one.
- *As-known-then reproducibility:* the cutoff lets a replay use only what had been retrieved by that time. Retrieval time is the knowledge boundary; publication time is separate and may be unknown (`UNKNOWN`, not backfilled).
- *Must appear on:* scan run; evaluation record; feature snapshot; setup outcome (as `outcome_data_vintage_id`, separate from the evaluation vintage because outcome windows use later data); parameter variant results; study result; prediction record; discovery run and research-brief snapshot; universe coverage snapshot. A result lacking a vintage reference is not reproducible and is not reportable.

**Value-state vocabulary (N10).** Carried from the importer into the logical model; defined per field observation. Detail and sample evidence in `IDX_SAMPLE_DATA_CONTRACT.md` §5A.
- Field value states: `OBSERVED` (non-zero or non-blank value), `OBSERVED_ZERO_CONFIRMED` (a zero whose meaning is supported by documented or cross-field evidence), `ZERO_AMBIGUOUS` (zero present, meaning not confirmed), `NOT_REPORTED` (source encodes absence as zero or blank), `NOT_APPLICABLE` (value cannot exist in that circumstance), `NO_QUOTE`, `UNAVAILABLE` (field absent from the source), `UNKNOWN`.
- Instrument-session status (separate axis): `REGULAR_ACTIVITY_REPORTED`, `NO_REGULAR_ACTIVITY_REPORTED`, and trading status `SUSPENDED_EXPLICIT` (only when a source states it) or `TRADING_STATUS_UNKNOWN`.
- Rules: no state is ever converted into numeric zero; none is read as bearish or as a signal by itself; a metric whose required input is `NOT_REPORTED`, `ZERO_AMBIGUOUS`, `NOT_APPLICABLE`, `NO_QUOTE`, `UNAVAILABLE` or `UNKNOWN` yields `UNDEFINED`/`INSUFFICIENT_DATA` for that row (a scan row becomes `UNEVALUABLE_REQUIRED_DATA_MISSING` when the input is a trigger input); aggregates exclude such rows and report the count by state; the value state is stored with the observation, flows into feature quality flags, scan reason codes, coverage counts and every displayed label.

**Universe status vocabulary (D-G).** `OBSERVED_ONLY` (rows actually present in accepted artifacts) vs `VERIFIED_AGAINST_MASTER` (reconciled with an independent official security master). No coverage percentage until the latter exists.
